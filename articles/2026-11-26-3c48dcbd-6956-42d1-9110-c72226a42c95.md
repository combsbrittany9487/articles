# 消息模板推送用 SSE 并在断线后自动重连

<!-- content-workspace-job:3c48dcbd-6956-42d1-9110-c72226a42c95 -->

## 问题场景

消息模板状态需要近实时更新，轮询开销大且延迟高，直接用长连接又容易在弱网下静默断开。

## 实现步骤

用 EventSource 订阅推送地址，监听 message 事件更新状态。

```javascript
function connect(url, onData) {
  let delay = 1000;
  const open = () => {
    const es = new EventSource(url);
    es.onmessage = (e) => { delay = 1000; onData(JSON.parse(e.data)); };
    es.onerror = () => { es.close(); setTimeout(open, delay); delay = Math.min(delay * 2, 30000); };
    return es;
  };
  return open();
}
```

监听 error，在连接关闭后按递增间隔重建，避免密集重试。

```javascript
const state = { count: 0 };
const es = connect('/api/template/stream', (msg) => {
  state.count += 1;
  document.querySelector('#template-badge').textContent = state.count;
});
```

## 注意事项

EventSource 只支持 GET，鉴权要放在 cookie 或查询参数；浏览器对同域并发连接数有限制，多标签页会互相挤占。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

在多人协作的项目里，应当限定作用范围避免影响其他业务，保证每一步都可验证。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

针对这类偶发问题，尽量把决策依据写进变更说明，便于横向对比不同方案的效果。

从长期维护角度看，先把最小可复现的用例固定下来，以便后续复盘有据可查。

遇到复杂链路时，先把最小可复现的用例固定下来，让排查路径更短。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

针对这类偶发问题，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。
