# 用令牌桶给发票接口做限流

<!-- content-workspace-job:905cbade-277a-4064-9749-d5d1afab6a7c -->

## 问题场景

发票的开放接口被合作方在整点集中调用，瞬时流量是平时的二十倍，下游直接被压垮。简单的固定窗口计数又会在窗口边界放过两倍流量。

## 实现步骤

令牌桶按固定速率补充令牌，桶容量就是允许的突发量。

```go
limiter := rate.NewLimiter(rate.Limit(100), 200)
if !limiter.Allow() {
    http.Error(w, "slow down", http.StatusTooManyRequests)
    return
}
```

按调用方维度分桶，避免一个客户把额度占满影响其他人。

```go
var (
    mu      sync.Mutex

func of(key string) *rate.Limiter {
```

## 验证方法

以远超限额的速率压测，通过的请求数应稳定在设定速率附近。

## 注意事项

分桶表的键要设过期，否则海量调用方会把内存撑爆；限流是保护手段，被限流的请求要能快速失败，不能让它继续占用连接。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

上线初期，要把边界条件列成清单逐项确认，让容量规划更有依据。
