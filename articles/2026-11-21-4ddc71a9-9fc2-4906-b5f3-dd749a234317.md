# 排查日志表写入时的死锁与重试

## 问题场景

日志表的批量任务偶尔报 Deadlock found，重跑又能过。日志里只有一句报错，不知道是哪两条语句互相等待。

## 实现步骤

先看引擎状态里的最近一次死锁详情，能看到两个事务各持有什么锁、在等什么锁。

```sql
SHOW ENGINE INNODB STATUS\G
```

查当前锁等待关系，确认是否还有正在僵持的事务。

```sql
SELECT * FROM performance_schema.data_lock_waits\G
```

把事务里的访问顺序统一，比如都按主键升序更新，能从根上消除大部分死锁。

```sql
SELECT trx_id, trx_state, trx_query
FROM information_schema.innodb_trx;
```

## 注意事项

死锁是数据库的正常保护机制，应用层仍要有重试；重试要加随机退避，否则同时重试会再次撞在一起。

如果数据量继续增长，优先用工具把现状量化出来再动手，防止出现隐性回归。

从成本角度看，应当限定作用范围避免影响其他业务，同时把结论沉淀进团队文档。

针对这类偶发问题，尽量把决策依据写进变更说明，让新人上手时少走弯路。

对于刚接手的同学，要明确各项资源的释放时机，确保线上行为始终可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

结合团队现状，可以通过日志补充上下文信息，保证每一步都可验证。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。
