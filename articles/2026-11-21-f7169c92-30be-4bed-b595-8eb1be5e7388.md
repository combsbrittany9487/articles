# 退款表深分页查询改用延迟关联

<!-- content-workspace-job:f7169c92-30be-4bed-b595-8eb1be5e7388 -->

## 问题场景

退款表的后台列表翻到几千页时接口直接超时，LIMIT OFFSET 越往后越慢，因为前面那些行虽然不返回，却照样要被读取和丢弃。

## 实现步骤

先用覆盖索引把目标页的主键捞出来，这一步不回表，扫描量可控。

```sql
SELECT id FROM refunds WHERE amount > 75 ORDER BY id LIMIT 20 OFFSET 200000;
```

再拿这批主键回表取完整字段，回表次数等于页大小，与偏移量无关。

```sql
SELECT a.* FROM refunds a
JOIN (SELECT id FROM refunds WHERE amount > 75
      ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

对比两次执行计划，改造后应当只走索引扫描而不是全表扫。

```sql
EXPLAIN ANALYZE
SELECT a.* FROM refunds a
JOIN (SELECT id FROM refunds ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
```

## 注意事项

延迟关联要求排序字段有序且能被索引覆盖，否则内层仍会 filesort；键集分页（记住上一页最后一个 id）比 OFFSET 更稳，但只支持顺序翻页。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

在跨团队协作时，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。
