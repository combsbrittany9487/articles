# 读懂指标表查询的 EXPLAIN ANALYZE 输出

<!-- content-workspace-job:e87e9c8e-541f-45af-b624-f24f14d322cc -->

## 问题场景

指标表的接口慢，看执行计划觉得没问题，因为看的是预估。预估行数和实际差了两个数量级，优化器据此选错了连接方式。

## 实现步骤

加 ANALYZE 拿到真实执行数据，逐节点的 actual time 是排查重点。

```sql
EXPLAIN ANALYZE SELECT * FROM metrics WHERE value > 512;
```

加 BUFFERS 看缓存命中，大量读磁盘说明缓存不够或扫描过多。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM metrics WHERE value > 512;
```

对比预估与实际行数，差距大就更新统计信息或调大采样比例。

```sql
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables WHERE relname = 'metrics';
```

## 注意事项

ANALYZE 会真实执行语句，写操作不要直接加；采样统计对倾斜数据不准，必要时对特定列调高统计目标。

从排障效率看，应定期回顾相关监控指标，降低同类问题再次发生的概率。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。
