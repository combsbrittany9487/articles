## 问题场景

短链导出要拉取多个分片再合并成一份文件，串行执行时总耗时随分片数线性增长。

## 实现步骤

按分片编号构造任务，提交到固定大小的线程池，池大小取分片数与 CPU 核数的折中。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def pull(part):
    rows = load_part("link", part)
    return part, len(rows), rows
```

每个任务只负责自己那段数据并返回结果对象，主线程用 as_completed 按完成顺序收集。

```python
def export(parts, workers=6):
    out = {}
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futs = {pool.submit(pull, p): p for p in parts}
        for f in as_completed(futs):
            part, n, rows = f.result()
```

## 验证方法

## 注意事项

线程池不适合 CPU 密集逻辑，GIL 会让加速比趋近于 1；任务里不要直接写同一个文件句柄，交回主线程统一写。

对于刚接手的同学，应定期回顾相关监控指标，以便后续复盘有据可查。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

上线初期，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

对稳定性要求高的场景，需要评估对现有调用方的影响面，以便快速定位瓶颈。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。
