# 给运单的 WebSocket 连接加心跳保活

<!-- content-workspace-job:30f6d1c8-a2bd-4548-a678-256d6c431122 -->

## 问题场景

运单的实时通知经常延迟几十秒才到，客户端以为自己还连着，其实连接早已被负载均衡器静默断开，浏览器还没触发 close 事件。

## 实现步骤

客户端定时发心跳，服务端收到就回，形成双向确认。

```typescript
const ws = new WebSocket(url);
ws.onopen = () => setInterval(() => ws.send(JSON.stringify({ type: "ping" })), 25000);
```

用标记位判断上一轮是否有响应，没有就主动关闭重连。

```typescript
let alive = true;
ws.onmessage = () => { alive = true; };
setInterval(() => {
  if (!alive) ws.close();
  alive = false;
}, 60000);
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

服务端的探活间隔要小于中间设备的空闲超时，否则还是会被切断。

```typescript
wss.on("connection", (s) => {
  s.isAlive = true;
  s.on("pong", () => { s.isAlive = true; });
});
```

## 验证方法

挂机十分钟后发一条消息，应能立即收到；人为断网后客户端应在两个周期内触发重连。

## 注意事项

浏览器不会因为网络中断立刻触发 close，只靠事件判断连接状态并不可靠；心跳频率过高会增加无谓流量，通常二十到三十秒一次比较合适。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在实际落地时，建议先在小流量环境验证行为是否符合预期，减少不必要的返工成本。

对于刚接手的同学，应定期回顾相关监控指标，以便后续复盘有据可查。

结合团队现状，可以通过日志补充上下文信息，保证每一步都可验证。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

上线初期，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。
