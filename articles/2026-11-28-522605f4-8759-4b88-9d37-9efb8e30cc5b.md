# 站点组件的行为用轻量 DOM 测试固定下来

<!-- content-workspace-job:522605f4-8759-4b88-9d37-9efb8e30cc5b -->

## 问题场景

站点组件改一次样式就担心逻辑被带坏，手工点页面回归又太慢。

## 实现步骤

用 jsdom 造一个最小文档环境，把组件挂到容器上。

```javascript
import { JSDOM } from 'jsdom';
const dom = new JSDOM('<!doctype html><div id="root"></div>');
global.document = dom.window.document;
```

断言渲染出的文本、类名与事件后的状态变化，不断言具体标签结构。

```javascript
export function mount(html) {
  const root = document.querySelector('#root');
  root.innerHTML = html;
  return root;
}
```

每个用例结束后清空容器，避免上一个用例的节点影响选择器。

```javascript
const root = mount('<p class="station">站点</p>');
console.assert(root.querySelector('.station').textContent === '站点', 'render');
console.log('cases', 1, root.children.length, 60);
```

## 注意事项

jsdom 不执行真实布局，依赖尺寸的断言要改用桩值；异步渲染要用 await 或宏任务等待后再断言。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，减少不必要的返工成本。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

对稳定性要求高的场景，需要评估对现有调用方的影响面，确保线上行为始终可控。
